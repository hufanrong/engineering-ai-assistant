# D18 · 重启接口改成 helper 之后：杀了服务，拉不起来（P0）

## 现象

v0.1.232 把 `restart_service()` 改成「分离 helper 进程，先起后死」（对应我上一单 D16 的 R1）。
调用返回：

```json
{"ok":true,"verified":false,"mode":"helper",
 "message":"已派发独立进程重启：约占端口的是当前进程本身（PID 21604），
            约 10 秒后旧进程会被结束并拉起新服务。
            可用 GET /api/update/restart/status 核对是否真换掉了。",
 "killed_pids":[],"will_kill":[21604],"port":8756}
```

然后：

| 时刻 | 状态 |
|---|---|
| 调用后 45 秒内 | `/api/status` **一次都没响应** |
| 调用后 60 秒 | `netstat` 里 8756 **无 LISTENING** |
| 调用后 80 秒 | 仍然无监听；`tasklist` 只剩一个无关的 pythonw(13700) |
| `updates/restart.log` | **没有新条目**（最后一条还是我 14:39:21 手工重启那次） |

**服务彻底没了，直到我手工 `start.py` 才回来**（8 秒后就绪，v0.1.232/62 文件）。

## 为什么比修之前更糟

| | v0.1.231 | v0.1.232 |
|---|---|---|
| 调重启 | 什么都不做，但服务**一直在** | 把服务**杀掉**，然后起不来 |
| 用户感受 | 点了没反应（轻） | **整个工作台消失**（重） |

原来只是「假成功」，现在升级成「真宕机」。

## 两个设计问题

### 1) 状态查询挂在被杀的进程上

提示让我用 `GET /api/update/restart/status` 核对 —— 但这个接口就在被杀的进程里。
**服务死了，接口自然也没了**，恰恰是最需要核对的时候查不到。

状态必须落到**文件**里（例如 `updates/restart_status.json`），
或者由 helper 自己写、由前端读文件，不能依赖 HTTP。

### 2) helper 没有失败出口

helper 杀完旧进程、拉起 `start.py` 之后，**没有任何人检查新进程是否真的起来了**。
`restart.log` 一条没写，说明 helper 的 stdout/stderr 根本没重定向到文件
（或者 helper 自己就崩了）。

至少要：
1. helper 全程写 `updates/restart.log`（含它自己的 argv、要杀的 pid、拉起命令、退出码）；
2. 拉起后轮询 `/api/status`，最多等 120 秒；
3. 起不来就**再拉一次**，还不行则写一条明确的失败记录；
4. 拉起失败时**不要已经杀掉旧进程**——做不到「先起后死」，就不要杀。

## 复现

```bash
curl -s --noproxy '*' -X POST http://127.0.0.1:8756/api/update/restart \
     -H 'Content-Type: application/json' -d '{}'
sleep 60
netstat -ano | grep 8756        # 无 LISTENING
tail -5 workbench/updates/restart.log   # 无新条目
```

## 验收

1. 调重启后 30 秒内 `/api/status` 可用且 PID 已变；
2. 起不来时**旧进程仍然活着**（宁可不重启，也不能宕机）；
3. `restart.log` 有本次 restart 的完整记录（含失败原因）；
4. 状态查询不依赖 HTTP，服务死了也能读到「上次重启结果」。

# D19 · 每轮遗留一个测试项目，还删不干净

## 现象

21:04 那轮结束后，`data/projects/` 里有 3 个项目：

```
0c9a4b2d  马诺诺              62 文件   ← 老板的真实项目
a80dfc88  自测_20261110_164520  60 文件   ← 16:45 那轮留下的
c8c39eee  自测_20261110_210452   0 文件   ← 21:04 那轮留下的
```

老板 2026-11-10 明确要求「用于测试的项目后续不再使用的话直接删除」。
现在**每跑一轮就多一个**。

## 两个不同的删不掉

### (a) 宿主安全策略拦下整批删除

```
[safe-delete][SAFE_DELETE_BULK_CONFIRM_REQUIRED]
{"count":147,"threshold":50,"scope":"turn",
 "targets":["D:\\fangong-workbench\\workbench\\data\\projects\\a80dfc88"],
 "targetCount":1}
```

`a80dfc88` 的 API 报 `file_count=60`，**磁盘上实际 147 个**（uploads + parsed_cache + vector_db）。
宿主守卫按「每次操作删除的文件数 > 50 需确认」拦下，于是自测收尾**静默失败**，
项目原地留着。

> 注意：我自己用 `/api/projects/delete` 删 `a80dfc88` 是成功的（147 也被拆成多批？），
> 说明拦截与调用来源/时序有关，不是稳定可复现的路径 —— 更需要产品侧显式分批。

### (b) 自己占着文件，删一半就停

删 `c8c39eee` 时：

```json
{"ok":false,
 "error":"项目资料删除失败：PermissionError: [WinError 32] 另一个程序正在使用此文件：
          '...\\c8c39eee\\vector_db\\cdfb936f-...\\data_level0.bin'；残留 18 项：[...]",
 "deleted_id":"c8c39eee","data_deleted":false,"partial_delete":true}
```

根因：这一轮里 `c8c39eee` 一度是**当前项目**，服务把它的 chroma 库打开了；
21:14:17 指针切回马诺诺时**没有 close 客户端**，`data_level0.bin` 一直被占。
`_safe_rmtree` 重试 3 次也拿不回来（占用者是同一进程，重试无意义）。

服务重启后才删得掉 —— 也就是说：**用户想删自己刚用过的项目，必须先重启。**

## 修复建议

1. **删项目前先 close 该项目的向量库/索引句柄**（若它是当前项目，先 `set_current` 再 close）；
2. `_safe_rmtree` 遇到 `WinError 32` 时，**先尝试释放本进程内的句柄**，而不是傻重试；
3. 删除**分批**（每批 ≤ 40 个文件），避开宿主 bulk-delete 守卫；
4. `partial_delete=true` 时应当**自动重试一次**并把残留清单写进日志，不要只返回给调用方；
5. 自测收尾删测试项目失败时，**必须让本轮报告变红**——现在它只写一行日志，报告照样 P50。

## 验收

1. 跑完一轮，`data/projects/` 里只剩真实项目；
2. 删除当前项目不需要重启服务；
3. 删除失败时报告里有独立断言变红，不再静默。

# D20 · 新扫描下，车间名 9/10 是废字（人工指定把它盖住了）

## 现象

阶段 1 断言「车间名合法」：

```
实际：可疑 9/10：['中矿堆', '主减速机油站', '件与件之间', '减速机润滑站',
                  '液压站', '相国四站', '相对室', '磨辊加载液压站', '磨辊润滑站']
```

而这一轮结束、查真实项目时：

```
中矿堆 files=0 devices=12
未归车间 files=13
熟料粉磨装置 files=46
相对室 files=1
粗碎车间 files=2 devices=12
```

只有 5 个，且熟料粉磨 46 个归得挺齐。

## 差在哪

| | 自测跑的那个项目 | 老板的真实项目 |
|---|---|---|
| 归类来源 | **全新自动扫描** | 46 个里有 **39 个是人工手动指定** |
| 结果 | 9/10 车间名是废字（液压站/油站/件与件之间/相对室） | 看着干净 |

**真实项目之所以"干净"，是老板自己点了 39 次点出来的，不是系统认出来的。**
一个新用户把资料拖进去，看到的就是左边那一列。

这条与 D13（车间名废字）、D15（熟料粉磨归类）是同一个病根的三种表现：
`_WORKSHOP_RE` 把设备名（液压站/油站）和正文碎片（件与件之间/相对室）当成车间名。

**建议 D13/D15 一起修，修完这条断言自然转绿。** 在那之前，它应该保持红色 ——
它如实反映了"新用户看到的界面"。
