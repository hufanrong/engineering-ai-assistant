# 从「服务一个项目」到「服务多个工程」· 平台化改造建议

> 老板 2026-11-12 定调：**「你给他数据只是为了让他建立一个可以供多个施工项目使用的 AI 平台，不是只用于某一个项目。」**
>
> 本文把这个要求翻成可执行的架构判据与改造清单。前一轮我给的车间口径（`20261112_080000_decision_workshop_policy`）是**产品行为**，属于平台规则，仍然有效；但里面引用的具体车间名、具体门槛属于**项目数据**，不应当进代码。

---

## 一、唯一判据

> **换一个工程，不改一行进程代码，只加/换一份配置，就能把新台账吃下来、把新图纸归好类。**

达不到这条，就是"给马诺诺定制的一套工具"，不是平台。所有下面的建议都服从这条判据。

---

## 二、现状：一层已经对了，一层还错着

### 已经对的：平台层物理位置存在

`app/platform_store.py` 开头写得很清楚：

```
国标/规范/通用文件独立建库，与子项目解析库分开（多项目共享）
新电脑安装时：导出 .fpglib 平台库包 → 导入即可复用全部规范库
```

**这说明"平台库"这个概念、目录、迁移机制都已经有了。** 只是目前里面只装「规范文件」，**没装「解析规则」**。

这是最省力的落点：解析规则（profile）就该放进 `PLATFORM_DIR` 同层，跟着平台一起迁移，而不是散在 `app/` 的代码里。

### 还错着的：解析规则被硬编码 + 隐含假设

`app/equipment_merge.py:73-91`：

```python
tag  = str(row.get("位号") or row.get("设备位号") or row.get("设备编号") or row.get("编号") or "").strip()
name = str(row.get("设备名称") or row.get("名称") or row.get("品名") or "").strip()
...
if h in ("位号", "设备位号", "设备编号", "编号", "tag", "TAG"): ...
elif h in ("设备名称", "名称", "品名"): ...
```

两个致命点：

1. **列名是 6 个硬编码字面量。** 换一个设计院，表头写「位号 / 设备名称」能过；写「设备编号 / 规格型号」就只有 tag 能过、name 全空；写「编号 / 名称 / 规模型号」勉强过；写「设备代号 / 设备名」直接全军覆没。
2. **`row` 是 `parse_excel` 输出的 `{表头: 值}` dict。** 也就是说**一切依赖「表头行被正确识别」**。表头识别错 → dict 的键全是错的 → 后面所有 `row.get(...)` 全空 → 整表判空。火法表 3709 行判空、`ledger_skipped_rows=200` 全是"台账空行"，根因就在这一层，不在判空逻辑本身。

**所以 D29 不是"某张表没读进来"，是"每接一个新工程都要改代码"。** 这条我单独编为 **D30（架构债）**，D29 应连它一起修。

## 三、三层分层模型

| 层 | 装什么 | 换工程时 | 落点 |
|---|---|---|---|
| **L1 框架** | 表头探测器、列映射引擎、主/参行判定、多 sheet 展开、候选队列与审批流、索引与关系模型 | **不动** | `app/` 代码 |
| **L2 行业包** | 矿业/冶炼/房建各自的术语词表、设备分类、常用表种模板 | 换行业才换 | `app/profiles/industries/*.yaml` |
| **L3 项目配置** | 台账适配器 profile、组织单元命名习惯、编号规则、验收门槛 | **每个工程一份** | `DATA_DIR/projects/<id>/profile/` |
| **L4 项目数据** | 文件、图纸、设备、现场记录 | 完全隔离 | `DATA_DIR/projects/<id>/` |

关键原则：
- **L1 里不许出现任何具体工程名词**（"熟料粉磨""马诺诺""2A24A47DDA"）；
- **L3 里不许出现任何代码逻辑**（只有数据）；
- L3 的 profile 要能**导出/导入**，像 `.fpglib` 那样跟着平台走，新工程直接拷一份改。

## 四、五个方法论

### M1 · 表头行探测（解决"表头不在第 1 行"）

```
for r in 1..20:
    score[r] = Σ 权重(列名 r 行里命中的字段)
    字段词表（L2 层可扩展）：
      编号类   设备编号/位号/设备位号/编号/代号/TAG     权重 3   ← 主锚点
      名称类   设备名称/名称/品名/设备名/规格型号       权重 3
      数量类   数量/台数/单位/单重                      权重 2
      参数类   型号/技术参数/功率/材质/规格              权重 1
    表头行 = argmax(score)
    若 max(score) < 阈值 → 不判空，标记 ledger_unparsed + 原因，推给人工配 profile
```

**要点：低于阈值时绝不静默判空。** 现在"判空 200 行"就是静默失败的典型——用户完全不知道发生了什么，只有我这边挖 `index.json` 才看得出来。

配套：`ledger_skipped_rows` 的 reason 要能区分「真空行」与「未识别表头」，这两种在业务上完全不是一回事。

### M2 · 列映射 profile 化（解决"换工程就失效"）

`DATA_DIR/projects/<id>/profile/ledger.yaml`：

```yaml
version: 1
name: "马诺诺锂矿-火法工艺设备表"
match:                        # 什么文件用这份 profile
  filename_regex: "工艺设备表|设备表"
  sheet_names: [".*"]         # 通配
header:
  search_rows: [1, 20]
  min_score: 6
columns:
  tag:   ["设备编号", "位号", "设备位号", "编号", "代号"]
  name:  ["规格型号", "设备名称", "名称", "品名", "设备名"]
  model: ["型号", "规格型号", "规模型号"]
  qty:   ["数量", "台数"]
  unit:  ["单位"]
  power: ["功率", "功率(kW)"]
  weight:["单重", "单重(kg)"]
org_unit:
  from: sheet_sub_item          # 取 sheet 内「子项名称」字段
  fallback: filename
  level_names: ["装置", "车间", "工段", "系统"]   # 组织单元后缀，随工程改
data_rows:
  primary_key: tag_nonempty     # 编号非空 → 主设备行
```

**注意 `columns.name` 里我把「规格型号」放在第一位。** 火法表这一列装的其实是设备名称（`板链斗式提升机`），而真正的型号在下面的参数行（`型号 NE150`）。这类"列名与内容不符"的情况在施工图设备表里很常见，profile 要允许一个字段吃多个候选列并**记下实际命中哪一个**，方便人工核对。

### M3 · 主设备行 vs 参数行（解决"一行设备被拆成十行"）

火法表 0205 的真实结构：

```
R7  CF0205ME01        | 板链斗式提升机 |  | 台 | 1 | 16000   ← 主行（编号非空）
R8                    | 型号           | NE150              ← 参数行
R9                    | 能力           | 90   | t/h         ← 参数行
R10                   | 提升高度       | 20.4 | m           ← 参数行
R14 CF0205ME01-DR1    | 电机           |  | 台 | 1         ← 主行（子件）
```

**判定规则：编号列非空 = 新设备；编号列空 = 上一台设备的参数行。**

这条规律对国内设计院工艺设备表几乎普遍成立，可以作为 L1 默认规则，同时允许 profile 覆盖（少量表会把编号合并单元格跨行，要先还原合并单元格再判）。

副产物：参数行不该被当成设备计入 `devices`，也不该触发"空行"告警——它们是有内容的，只是没有编号。**当前把它们算进"空行 200 条"，是把正常结构误判成脏数据。**

### M4 · 多工作表独立展开

一个 xlsx 里 10 个 sheet 不是异常，是常态（每个子项一张）。

- 每个 sheet **独立探测表头行**，不假设一致；
- sheet 内的「子项名称 / 单元名称 / 装置名称」字段 → 天然的**组织单元来源**，优先级**高于**从文件名猜；
- sheet 名本身也是强信号（`0205`、`0201-脱硫脱氟`），可作为组织单元编号；
- 合并汇总时保留 `(sheet, row)` 溯源坐标，出问题能直接定位到单元格。

### M5 · 先规整再映射（解决"列号硬编码"）

火法表同一个文件里：`0101` 的 A 列是设备编号，`0205` 的 A 列空、B 列才是设备编号。

**所以绝不允许按列号取数。** 顺序必须是：

```
读原始矩阵 → 还原合并单元格（左上值填充）→ 去全空行/全空列 → 探测表头行 → 按表头文字定位列 → 取值
```

另外：火法表 `max_column` 达到 **252**，绝大多数是空列或格式残留。规整后再做映射，性能与准确率都会明显改善。

## 五、复用性验收（这条最要紧）

**只用马诺诺验是不够的**——把火法表喂通了，很可能只是把火法表的特征写进了代码，下一个工程照样死。

建议造一个**合成工程**做回归，专门用来打"平台性"：

| 维度 | 马诺诺（真实基准） | 合成工程（复用性） |
|---|---|---|
| 表头行 | 第 6 行 | **第 3 行** |
| 列名 | 设备编号 / 规格型号 | **位号 / 设备名称 / 规模型号** |
| 组织单元叫法 | 车间 / 装置 | **标段 / 区域** |
| sheet 数 | 10 | **2**（一个规整、一个含合并单元格） |
| 编号规则 | 2A24A47DDA0205ME1M | **任意，如 ABC-01** |

**通过标准：不改一行代码、只加一份 profile，两条数据都能吃下**，设备数、组织单元数与预期完全一致。

做不到就说明还有项目特征漏在 L1 里。这个合成工程可以很小（20~30 行假数据），但它是**唯一能证明"能换工程"的东西**。

## 六、改造清单（按性价比排序）

| 序 | 动作 | 落点 | 解决 |
|---|---|---|---|
| 1 | 抽出 `ledger_adapter.py`：探测表头行 + 按 profile 映射列 + 主参行判定 + 多 sheet 展开 | 新建 `app/` | D29 / D30 主体 |
| 2 | 把 `equipment_merge.py:73-91` 的 6 个字面量替换为从 profile 读 | 改造 | 换工程失效 |
| 3 | `ledger_skipped_rows.reason` 区分「真空行 / 未识别表头 / 无编号参数行」 | 改造 | 静默失败 |
| 4 | profile 目录纳入项目备份与导出（跟 `.fpglib` 一个思路） | 改造 | 迁移复用 |
| 5 | 合成工程回归套件 | 新建测试 | 平台性证明 |

排序理由：先做 1 和 2，D29 立刻能通；3 解决"下次还是查不出来"；4、5 是把平台性固化下来的机制。
