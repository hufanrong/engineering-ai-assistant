# 车间归类口径 · 实现规格（老板 2026-11-12 拍板）

> 这不是建议，是口径。开发端按此实现，我方按此验收。

## 一、老板原话与拆解

> **「自动归类到已确定的车间，不确认留存让人工确认。」**

拆成两条硬规则：

| 规则 | 含义 |
|---|---|
| **R1 只认已确定** | 只有**已确定的车间**才允许自动归类。已确定 = 设备台账来的 + 人工确认过的。**两个来源，仅此两个。** |
| **R2 拿不准就留存** | 匹配不上、或拿不准的，一律进待确认队列留存，等人工签。**不许自动进正式车间清单。** |

配套两条体验要求（同样是硬要求，否则 R2 等于没做）：

| 规则 | 含义 |
|---|---|
| **R3 待确认要被看见** | 「待确认 N 个」必须有显眼入口，不能埋在二级页面。看不见的队列等于没有。 |
| **R4 签一次就够** | 人工确认后即转正（含别名绑定），此后同类文件自动归类，**不许问第二遍**。 |

---

## 二、判定流程（每个文件 / 每条设备记录）

```
① 提取候选车间名
     来源优先级：台账「子项名称」 > 文件名/路径 > 文档内容

② 与「正式车间白名单」比对
     命中（精确，或命中已绑定别名）
        → 自动归类，assigned_by = "auto"     ← 属于 R1
     未命中
        → 写 workshop_candidates，status = pending
        → 文件保持「未归类」
        → 不进入正式清单                      ← 属于 R2

③ 人工确认
     → 白名单追加该名，confirmed_by = "human"，记 confirmed_at
     → 该候选名下已挂的文件批量归类
     → 之后同类文件走 ② 的"命中"分支          ← 属于 R4
```

**执行顺序是前提，顺序错了整套会空转：**

```
先导设备台账 → 用台账「子项名称」建立白名单 → 再自动归类文件 → 剩余推待确认
```

台账没进来，白名单就是空的，自动归类必然把**所有**文件推成待确认。当前就是这个状态（`devices=24`、`workshops=2`、候选队列 0），根因是 D29。

## 三、数据结构建议

`workshop_registry.json`

```json
{
  "workshops": [
    {"name": "熟料粉磨装置", "source": "ledger", "from_ledger": true,
     "confirmed_by": null, "confirmed_at": null, "aliases": []},
    {"name": "中矿堆", "source": "ledger", "from_ledger": true,
     "confirmed_by": null, "confirmed_at": null, "aliases": ["中矿堆场"]},
    {"name": "XX 车间", "source": "human", "from_ledger": false,
     "confirmed_by": "hufanrong", "confirmed_at": "2026-11-12 08:00", "aliases": []}
  ]
}
```

`workshop_candidates.json`

```json
{
  "candidates": [
    {"name": "粗碎车间", "hit_count": 3,
     "first_seen": "2026-11-10 07:51", "last_seen": "2026-11-12 07:23",
     "sample_files": ["..."], "status": "pending",
     "reason": "不在正式车间清单，且未经人工确认",
     "suggest_candidates": ["返回不存在的近义车间名，供人工点选"]}
  ]
}
```

关键：`suggest_candidates` 要能给出近似的已有车间名，让人工**点一下就签约**，而不是手打。这一条决定了 R3 是不是真的可用。

## 四、对现有缺陷的直接约束

### D27（P2）—— 按新口径必须改

现状（本轮唯一失败断言）：

```
正式车间 ['中矿堆','粗碎车间'](已归类 0 文件)
待审批候选 ['粗碎车间'](临时归类 2 文件)
混入 = ['粗碎车间']
```

`/api/workshops` 里 `粗碎车间` 的 `from_ledger = false`，**却仍在正式清单**。

→ 按 R1/R2：`from_ledger=false` 且 `confirmed_by` 为空的名字，**不得出现在正式车间清单**，必须降级为待确认。
→ 验收判据：**任何 `from_ledger=false` 且未确认的名字出现在正式清单，即判失败。**

### D29（P0）—— 白名单的来源

火法表 10 个 sheet 的「子项名称」就是天然的正式车间名，应作为 `from_ledger=true` 的白名单基底：

```
0101 锂辉石库 · 0103 锂辉石烘干 · 0104 锂辉石计量
0201 回转窑尾装置 · 0202 回转窑中装置 · 0203 回转窑头装置
0203 熟料送存仓(0204) · 0205 熟料粉磨装置
0201-尘硝一体 · 0201-脱硫脱氟（子项名称为空，需回退到文件名或转待确认）
```

台账先把这 8~10 个名字建立起来，后面 62 个文件的自动归类才有依据。

## 五、验收口径（老板已认可，四条同时满足）

拿 `火法部分工艺设备表（0430).xlsx`（10 sheet / 3709 行 / 表头均在第 6 行）做回归基准：

| 指标 | 门槛 | 现状 |
|---|---|---|
| 设备总数 | **≥ 600 台** | 24 |
| 识别车间数 | **≥ 8 个** | 2 |
| 位号非空率 | **≥ 90%** | 未达标（台账未入库） |
| 熟料粉磨装置单车间 | **≥ 60 台** | 0 |

**四条同时满足才算通过；任一不达标即判失败，不接受"部分通过"。**

另加两条本项目特有的口径验收：

| 判据 | 说明 |
|---|---|
| **C1 无未确认名字混入正式清单** | 遍历 `/api/workshops`，`from_ledger=false && confirmed_by=null` 的条目数必须为 0 |
| **C2 待确认可追溯** | 每个候选必须能查到：出现次数、首次/末次时间、来源文件样本；人工签完必须从候选消失并出现在正式清单 |

## 六、三处边界（老板口述未覆盖，**我不擅自定**，请裁定）

| # | 情形 | 选项 A | 选项 B | 我的倾向（仅供参考，不作决定） |
|---|---|---|---|---|
| E1 | 一个文件命中**多个**已确定车间 | 取台账子项名优先的那个，其余忽略 | 整份进待确认，让人工指 | 倾向 B：老板的规则本质是"拿不准就别猜"，多命中就是拿不准 |
| E2 | 台账自身带来的新车间名（如 0203 回转窑头装置） | 直接进正式清单（`from_ledger=true`），免人工 | 也要人工签一次 | 倾向 A：台账是权威骨架，若台账都要签一遍，8 个车间手工签 8 次，违背"签一次就够"的初衷 |
| E3 | 匹配时是否放宽到"去后缀/去空格后相同"（如「熟料粉磨」≈「熟料粉磨装置」） | 放宽，减少待确认量 | 只认精确 + 人工绑定的别名 | 倾向 B：放宽会重新引入"猜名字"的老毛病，宁可多推几条待确认 |

这三条定了，实现就没有歧义。**E2 影响最大**——它决定导入台账后要不要人工签 8~10 次。

## 七、回归用例建议

1. **空项目**：无台账 → 扫 62 个文件 → 正式车间数必须是 **0**，候选数 ≥ 1，且**一个文件都不得被归类**（因为白名单为空）；
2. **先导台账再扫**：正式车间 ≥ 8（全 `from_ledger=true`），C1 判据通过；
3. **人工签一个候选**：该候选从队列消失、进正式清单、名下文件被归类；重启服务后签名不丢；
4. **反向**：手工往 `workshop_registry.json` 塞一个 `from_ledger=false` 的条目 → C1 判据必须报红（证明闸门真的在拦，不是摆设）。
