# D35 · 删除项目时 vector_db 漏删，且接口谎报「资料已删除」（P1）

> 发现时间：2026-11-13 07:36 ｜ 版本：v0.1.246
> 发现场景：按老板指令清理自测残留项目时，核对磁盘发现

## 1. 现象

删除前 4 个项目 → 走正规接口删掉 3 个自测项目，接口全部返回 `data_deleted: true`，项目列表也确实只剩马诺诺。**但磁盘上还留着一个已不存在的项目目录。**

```
D:\fangong-workbench\workbench\data\projects\
  0c9a4b2d\        ← 马诺诺（保留）
  f95c1a30\        ← 列表里已无此项目，但目录还在，15M
```

`f95c1a30` 的解剖：

| 项 | 状态 |
|---|---|
| `project_meta.json` | **不存在**（元数据已清） |
| `index.json` | 存在，但 **0 条目** |
| `vector_db/` | **存在，15M** |
| 目录 mtime | **2026-11-13 04:29** |

04:29 这个时刻是关键：它与本轮自测（`自测_20261113_040635`）收尾、以及**服务进程无痕消失**是同一分钟（见 `reports/20261113_071000_check_update/` D34）。

## 2. 对照组

本次同时通过同一接口删除了三个自测项目（`ebf7bfbd` / `0a0bd124` / `1f4e9819`），删除后核对 `projects/` 目录：**三个目录全部消失，无任何残留，每个 15M 确实释放**。

差别在哪：那三个项目删除时**服务处于空闲、未持有该项目的 chroma 句柄**；而 `f95c1a30` 被删时，服务刚扫完/正在向量化，`data_level0.bin` 处于打开状态。

→ **结论：漏删与「删除当时是否持有 chroma 文件句柄」直接相关。这正是 D19 的根因（chroma `PersistentClient` 不释放 `data_level0.bin`），在删除路径上没有被彻底兜住。**

## 3. 为什么这条比「删不掉」更糟

删除失败本身可以接受（可以用重启释放句柄后重试）。真正的问题是**接口说了假话**：

```json
{"ok": true, "message": "项目「…」已删除（含项目资料）", "data_deleted": true, "log_written": true}
```

用户看到「已删除（含项目资料）」，实际磁盘上还压着 15M。这类「静默漏删 + 谎报成功」在工程场景里的代价是：硬盘一天天变满、备份越做越大、迁移时把死数据一起搬走，而且**没有任何一处记录能解释这些目录是怎么来的**。

同样的模式在你们自己的注释里已经点过一次（`reparse_file` 那段：「这类『静默失败 + 谎报成功』比直接报错更难查 —— 用户会以为是自己操作不对」）。删除路径上又复现了一遍。

## 4. 修法（三步，都不大）

1. **删除前显式释放**：删除 `vector_db` 之前调用 chroma client 的 `close()` / 置空单例，或直接把该项目的 `VectorStore` 实例从缓存里剔除。如果架构上拿不到实例，退一步：删目录失败时**不要吞异常**。
2. **删除后校验**：`delete_project` 收尾处加一次 `os.path.exists(project_dir)`；仍存在则
   - 返回 `data_deleted: false`，并在返回体里给出 `residual: ["vector_db"]`；
   - 写进 `operation_log`：「删除未删净，残留 vector_db，原因：WinError 32 文件占用」。
3. **可重试机制**：因为这是「句柄占用」类失败，最有效的兜底是**登记待清理队列**，服务重启后（句柄天然释放）自动补删一次。这比让用户手动重启再点一遍删除体验好得多。

## 5. 验收口径

| 指标 | 门槛 |
|---|---|
| 服务**正在扫描/向量化**时删项目 | 目录 100% 消失，或返回 `data_deleted=false` + 残留清单 |
| 服务空闲时删项目 | 目录 100% 消失（本次已实测通过） |
| 删除后 `projects/` 下孤儿目录 | 每次删除后扫一遍，必须为 0 |
| 谎报 | 接口返回 `data_deleted=true` 而目录仍在 → 判缺陷 |

建议加一条**回归套件**：造一个项目 → 启动扫描/向量化占住句柄 → 并发调删除 → 断言「要么删净，要么如实报残留」。现有 `test_delete_sweep`（15/15 通过）覆盖的是「服务空闲」场景，所以它绿而现场漏删——这与 D23 的「套件绿而产品红」是同一类问题。
