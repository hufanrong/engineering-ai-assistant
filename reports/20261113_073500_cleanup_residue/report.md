## 二、发现 D35：删除时 vector_db 漏删，接口却说「资料已删除」

三个项目走接口删得干干净净，但磁盘上还留着一个**列表里根本不存在的项目目录** `f95c1a30`：

```
无 project_meta.json（元数据已清）
index.json 0 条目（索引已清）
vector_db/  15M  ← 只有它没删掉
mtime 2026-11-13 04:29  ← 与「服务进程无痕消失」同一分钟
```

**对照组说明不是普发**：本次删除的三个项目在服务空闲时执行，整目录删净、无残留；`f95c1a30` 被删时服务刚扫完/正在向量化，`data_level0.bin` 被 chroma 打开着。

→ **这就是 D19 的根因（chroma `PersistentClient` 不释放 `data_level0.bin`）在删除路径上没兜住。** `test_delete_sweep` 15/15 全绿，因为它测的是空闲态——与 D23「套件绿而产品红」同一类问题。

**比「删不掉」更糟的是谎报**：接口返回 `"data_deleted": true`，用户以为删干净了，实际盘上还压着 15M，而且没有任何记录能解释这目录怎么来的。

修法三步（详见 `defects_D35.md`）：删除前显式释放 chroma 句柄 → 删除后 `os.path.exists` 校验，未删净就 `data_deleted=false` 并返回残留清单 → 登记待清理队列，服务重启后自动补删。

## 三、建议增加的回归

「造项目 → 启动扫描/向量化占住句柄 → 并发调删除 → 断言：要么删净，要么如实报残留」。现有 `test_delete_sweep` 只覆盖空闲态。
