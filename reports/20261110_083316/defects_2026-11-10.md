# 2026-11-10 真实资料实测 · 缺陷清单与修复对照

> 本轮改用**马诺诺项目的真实工程资料**（老板 2026-11-10 指令：清掉自测项目残留，以后测试都用马诺诺资料），

> 其中 25 张 DWG、30 份 PDF（16 份为图形 PDF）、3 个 .xls 箱单、2 个 .xlsx 台账、1 个 rar、1 个 zip。

## 一、最严重：资料库索引整批覆盖，已解析文件凭空消失

**现象**（实测时间线，同日同一项目 0c9a4b2d）

| 时刻 | 磁盘 uploads | parsed_cache | index.json | 前端列表 |
|---|---|---|---|---|
| 07:57 | 65 | 57 | **51** | 51 |
| 08:05 | 65 | 57 | **43** | — |
| 修复后 | 65 | 57 | 62 | 62 |

parsed_cache 里明明有 57 份解析结果，`index.json` 只剩 43 条 —— **14～19 个文件解析成功、缓存还在、
正文还读得出来，但在资料库里根本不存在，界面上一个字都不报**。老板的观感就是「我传了，怎么看不到」。

**根因**：`/api/upload-files` 在函数开头 `idx = scanner._load_index()` 拿一份快照，整批传完才
`_save_index(idx)`。一次几十个大 DWG/PDF 要跑 5 分钟以上，这几分钟里任何别的写入
（另开一批上传 / `/api/scan` / 设备同步）都会被批次末尾那次「旧快照整份覆盖」抹掉。
`_save_index` 的锁只保证「这一次写」原子，管不住「调用方手里的快照已经过期」。

**修复**（主代码库）

- `app/scanner.py::merge_index_entries()` —— 锁内「读最新 → 只覆盖自己的键 → 写回」，新增接口；
- `app/main.py::upload_files()` —— 从「整批末尾写一次」改成**每 5 个文件或每 5 秒合并一次**，
  去重判断同时看 `seen`（已落盘）与 `pending`（待落盘）；
- `app/scanner.py::reconcile_index()` + `app/main.py:/api/index/reconcile` —— 用 parsed_cache
  反向对账、把丢掉/中断留下的条目补回索引（`dry_run=true` 只报差额，不改盘）。

**验证**：对真实项目跑 reconcile，`index 43 → 补入 19 → 62`；`/api/status` 与前端文件列表
立刻从 43 变 62，与磁盘 62 个唯一文件一致；`/api/index/reconcile?dry_run=true` 现在恒返回 `added=0`，
已写成阶段 1 的常驻断言「索引与解析缓存一致」。

**顺带修掉的两个连带问题**

1. 大批量上传期间资料库一直不刷新（实测 07:53—07:54，cache 已到 48，界面始终显示 5）——
   用户会以为没传上去而重复上传；增量合并后边传边可见。
2. 浏览器关闭/网络中断导致批次中断时，本批已解析的文件全部丢失条目 —— 现在最多丢 5 个文件 / 5 秒。

## 二、`.xls` 完全没有支持，3 份现场箱单被当成「不支持」

**现象**：`熟料粉末斗提机.xls`、`江西华欣拉链机箱单.xls`、`滁州安瑞链板称箱单.xls`
上传后 `status=skipped`、`parser=unsupported`，内容一个字都没进库。

**根因**：`config.EXT_EXCEL = [".xlsx", ".xlsm"]` —— 老版 .xls 不在支持列表。
**并且**：这 3 个文件的真实内容是 **HTML 表格**（文件头 `<html xm...`），
是国内系统「导出 Excel」的产物，xlrd 直接报
`Expected BOF record; found b'<html xm'`。

**修复**

- `config.EXT_EXCEL_LEGACY = [".xls"]`（与 `EXT_EXCEL` 分离，避免被 openpyxl 分支命中）；
- `parsers/engines.py::parse_xls()` —— 双分支：真 BIFF 走 xlrd，HTML 表格走标准库 `HTMLParser`；
- `parser` 标为 `"excel"`，使设备台账归并（按 `parser=="excel"` 逐行取位号/名称）对 .xls 同样生效。

**验证**：3 个文件全部 `parsed`，分别解出 70 / 15 / 5 行；
`斗式提升机,NE150*22.9M`、`单证编号=MNN-HN-179`、`供应商名称=宜都大一重工有限公司` 均已入库；
用「宜都大一重工 斗式提升机 NE150」检索，前两条命中就是这个 xls。

## 三、精确编号检索排不进前 3

**现象**：查 `MNN-HN-179`（老板最常查的单证号），向量检索返回的是
`熟料磨风机箱单.pdf`(0.372)、`熟料磨箱单.pdf`(0.38) —— 真正含这个编号的
`熟料粉末斗提机.xls` 一条都没进前 3。同一个库，关键词检索能 3/3 全中。

**根因**：只有纯向量检索；编号这种低频 token 在几百个 chunk 里语义上不占优。
`search_keyword` 只在 embedding 报错时才当降级用。

**修复**（`app/main.py`）：查询里出现「编号形态」token（`MNN-HN-179` / 8 位以上订单号）时，
先跑关键词检索，把精确命中排在向量结果前面（按 sha+chunk 去重，不丢向量结果），
`retrieval` 标为 `vector+keyword`。

**验证**：`MNN-HN-179` → 首条 `3b4ea4f66837_熟料粉末斗提机.xls distance=0.0`，其余两条为另两份箱单。
纯语义查询（如「粗碎车间」）仍走 `vector`，不多付成本。

## 四、W25 张 DWG 显示「部分解析」，掩盖了「缺依赖」

**现象**：25 张 DWG 全部 `status=partial`、正文 0 字；实际上 `parse_cad` 明确设了
`status="failed"` + `error="未找到 ODA File Converter…"`，被 `parse_file()` 里一句
「没有 text/structure 就记 partial」无条件覆盖。

**修复**（`parsers/engines.py::parse_file`）：只有解析器自己给的是 `parsed` 时，
才允许降级为 `partial`；`failed` 原样保留。`failed` 与 `partial` 是两件事：
前者要装依赖/换格式，后者是文件里确实没那么多文字。

**结果**：这类文件现在会带明确原因进「失败/待处理」清单，而不是混在资料库里假装成功。

## 五、图形 PDF 无文本层（16 份），OCR 兜底在本机不可用

**现象**：30 份 PDF 里 16 份 `partial` + 正文 0 字，提示「PDF 无可提取文本层（可能是扫描件）」。
这些是立磨/液压站的厂家图纸，CAD 直接打印，文字被转成曲线。

**已做**：`config.PDF_OCR_FALLBACK` + `parsers/engines.py::_ocr_pdf_text()`
（PaddleOCR + pymupdf 渲染前 3 页，150dpi，120 秒预算）。

**本机实测结论（未解决，如实记录）**：
PaddleOCR 3.x 在这台机器上 `predict` 直接抛

```
NotImplementedError: (Unimplemented) ConvertPirAttribute2RuntimeAttribute not support
[pir::ArrayAttribute<pir::DoubleAttribute>]  (onednn_instruction.cc:118)
```

设 `FLAGS_use_mkldnn=0` 也复现，是 PaddlePaddle 的 oneDNN 后端问题，与 PDF 无关。
因此加了**熔断**：一次失败后本进程内不再重试（否则 16 份 PDF 每份白等 2～3 秒）。
现在首份 PDF 付 19.8s（模型加载），其余 1.9s 直接返回原因。
要真正解决需换 OCR 引擎（RapidOCR / PaddleOCR CPU 版特定版本 / 商业 OCR），待老板拍板。

## 六、启动脚本 `run_workbench.bat` 带 UTF-8 BOM

**现象**（对照实测，同一份内容）：
带 BOM → `'@echo' 不是内部或外部命令`，`@echo off` 失效，窗口刷满每条命令；
去掉 BOM → 正常。

**修复**：重写为无 BOM + CRLF、注释全 ASCII、中文只出现在 `echo` 里；
Python 探测链改为 venv → .venv → PATH → LOCALAPPDATA → 内置运行时（与 `open_or_start.bat` 一致），
并把「服务已在运行」做成显式分支，不再重复启动。

## 七、全绿轮次被判「失败」

**现象**：`20261110_071929` 全阶段轮次 P74/F0/S2（74 通过、0 失败、2 跳过），
含 AutoCAD 阶段 4 的 6/0/0、原图 MD5 未变、成果 PDF 5136B —— 却判 `failed`。
原因是 selftest 收尾删测试项目被环境拦下、`sys.exit(1)`，而 `wb_loop` 用退出码判状态。

**修复**（`tools/wb_loop.py`）：状态只看断言计数（未出报告=error / 有失败=failed / 否则 passed）；
断言全过但退出码≠0 时判 passed，同时把 rc 和可能原因写进报告，不隐瞒。
